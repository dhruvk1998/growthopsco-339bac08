# Offline writer revision — production on hold

## Architecture

Neither deployed script nor active routes/forms have changed. `proposed-submission-handlers.ts` contains **both replacement handlers**, not a live endpoint. Their only effects are through the authenticated Apps Script writer, optionally reached through one allowlisted same-key Lovable bridge. There are no direct Sheets, Gmail, Apps Script legacy, or FormSubmit fallbacks in the proposal. The live application still has its old bypasses and no durable protection; rollout is not complete.

The browser preparation helper persists key, submission ID, timestamp and business-payload hash across retries/refreshes. A changed pending payload fails closed pending reconciliation. Its storage contains identity/hash, not form details or secrets. At cutover, both forms must use this helper after hydration, retain identities for partial/ambiguous results, and provide an explicit independently safe new-request operation. Cleared storage, separate devices/tabs, or a genuinely new key are not deduplicated automatically. Browser persistence is not a server uniqueness constraint.

Every writer action authenticates before touching Google services. `submit` uses a server-only WRITER_TOKEN; `reconcile`/`finalize` use a separate operator-only OPERATOR_TOKEN. Both require at least 32 characters and distinct values. Secrets must be securely supplied, never put in browser bundles or source. Requests use HTTPS JSON bodies, never query-string tokens. The writer checks action-specific shapes, size limits, fixed owner recipient, prospect address, reply-to, assessment structure and recomputes the canonical SHA-256 hash. Missing configuration fails closed. Public Google web-app access does not imply unauthenticated privileged operations.

### Durable storage recovery

Under the script-wide lock, the ledger stores full recoverable payload and reserves a specific data row before writing it. Reservation coordinates future claims even when the data row is absent. The same data range, original fields and a trailing key/hash marker are written together; recovery checks this range rather than appending again. A lost response after data write therefore reads the original row back. Claims with no row reconstruct it from the saved payload. Conflicting, moved, manually edited or deleted verified rows stop with `data_conflict`; they are never overwritten or recreated blindly.

`Database` keeps its existing A:L fields and receives a writer marker in M. `Diagnostic Requests` keeps A:N, including Yes/New/blank notes, and receives a marker in O. Assessment details are retained in the ledger and original owner message without changing the contact's A:L columns. Formula-like user values are prefixed with a zero-width character to prevent formula execution. A new `Submission Ledger` uses Key + Record JSON v1; an older incompatible ledger blocks rather than being migrated destructively.

### Separate email outcomes

Persistence is `claimed`/`written`. Owner/prospect send states are independently checkpointed. Before each send, `sending` is saved and flushed. A restart seeing `sending`, or a MailApp exception, records `unknown` and never retries that send automatically. A completed call records `accepted`, with delivery still `unconfirmed`. Contact has only its owner message and original prospect reply-to; diagnostic has owner and prospect messages with unchanged wording and CA$199/manual/report terms.

Never-started messages, including quota-paused messages, can safely resume via same-key retry or operator `reconcile`. `finalize` cannot send; it records bounded operator evidence for accepted/delivered/bounced outcomes, or explicitly confirmed-not-sent before a later reconcile. Absence of a bounce or lack of a Sent copy is insufficient evidence to authorize a resend. MailApp exposes no per-message delivery reference; recipient confirmation or other independently matched provider evidence is required. The system cannot promise exactly-once email delivery.

Both offline handlers and the writer client require HTTP success **and** a validated JSON success contract with matching key. HTTP 200 `{ok:false}`, malformed JSON, HTML and wrong keys fail. Partial/ambiguous results are returned distinctly; send acceptance is not delivery. Existing honeypot and public-form abuse protections must be retained at route cutover, ahead of these validated-payload adapters.

## Automated evidence

Coverage includes every action's authentication, operator separation, malformed/rejected HTTP-200 bodies, claim/data/written checkpoints, each recipient's intent/send/result checkpoint, same-key arrivals/retries, lost responses, payload mismatch, quota pause, row conflicts, evidence-gated reconciliation, both adapters and identity-preserving bridges. No Google requests, real submissions or emails are used. These mocks cannot establish real LockService atomicity, Google execution interruption ordering or deployment permission behavior.

## Remaining limitations and rollout risk

LockService serializes cooperating instances of one script; Sheets has no unique constraint/transaction. External writes, row sorting/insertion/deletion or another script can break reservations and require manual reconciliation. The writer intentionally stops on conflicts. Ledger scan costs grow with volume; retention/access policy and quota monitoring are required. Saved JSON is bounded; oversized assessment/message combinations reject instead of silently truncating. A hard-stop after send cannot reveal whether Google accepted it, so unknown outcomes may require operator review indefinitely.

Preserving contact fields/notifications does **not** preserve its old independent fallback availability: the authoritative writer is a single dependency and MailApp sender identity/scopes may differ from the connected Gmail account. Verify these explicitly before replacing the fallback. Rolling back the website alone to old direct-write routes would bypass the ledger; pause intake and reconcile in-flight effects before rollback. Code rollback cannot undo rows or emails.
